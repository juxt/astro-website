# Adopt

Mature, well-supported approaches ready for production use.

<div data-radar data-label="Classical ML" data-ring="adopt" />

## Classical ML

Classical machine learning approaches such as random forests, gradient boosting (XGBoost, LightGBM), linear/logistic regression and support vector machines remain the best balance of explainability and efficiency for structured data problems. These techniques routinely outperform more complex approaches on tabular data while training faster and costing less to run.

Realising these benefits requires quality training data and staff with appropriate expertise. Unlike LLM-based solutions that have democratised AI for organisations without data science teams, classical ML demands specialised knowledge in feature engineering and model selection. For organisations with the necessary capabilities, these methods work well even with smaller enterprise datasets, matching or exceeding the performance of more complex approaches while remaining more interpretable and easier to maintain.

<div data-radar data-label="RAG" data-ring="adopt" />

## RAG

Retrieval-Augmented Generation (RAG) combines search and text generation to produce more accurate responses, grounding them in real data and reducing confabulation. It is valuable where accuracy and traceability matter, such as customer service or compliance. Implementation requires attention to document processing and embedding strategies, but tooling has lowered the barriers.

We're watching techniques such as [Self-RAG](https://arxiv.org/abs/2310.11511), which prompts the model to gather more evidence or refine its responses; early results suggest it reduces confabulations further.

For coding agents working over a live codebase, the calculus has changed. Anthropic's Claude Code team [found](https://github.com/nibzard/awesome-agentic-patterns/blob/main/patterns/agentic-search-over-vector-embeddings.md) that agentic search, grep, glob and reading files directly, outperformed a pre-built embedding index, and Claude Code deliberately does not embed the codebase: an index goes stale as code changes, and conceptually similar matches without a shared token are usually noise. The lesson is scoped. For grounding over document corpora, RAG remains the right tool; for navigating code, direct search often beats retrieval.

RAG introduces an indirect prompt injection attack surface. Retrieved documents are injected into model context, so adversarial content in any document reaches the prompt via the retrieval step. Retrieval access controls and provenance tracking for ingested documents help mitigate this risk.

See also: Cross-encoder reranking, Structured RAG, Hypothetical document embeddings (HyDE).

<div data-radar data-label="LLM-as-a-judge" data-ring="adopt" />

## LLM-as-a-judge

LLM-as-a-judge has proven one of the most practical techniques for evaluating AI system outputs. Today's strongest models provide nuanced, multidimensional critique that simpler evaluation methods cannot match, except for very constrained metrics such as exact match or BLEU scores.

The technique is widely adopted in both offline and online evaluation. Offline, it scales far better than human assessment, allowing teams to test thousands of outputs quickly. Online, an LLM judge can evaluate another LLM's output in real-time, enabling dynamic workflow adjustments based on quality assessments.

[Research demonstrates](https://arxiv.org/abs/2306.05685) that frontier models provide judgements correlating strongly with human preferences across many evaluation dimensions. We recommend using a different LLM as the judge than the one being evaluated, and viewing this as an augmentation to human evaluation rather than a replacement. The strongest LLMs can identify nuanced issues in reasoning and factuality that would otherwise require substantial human review time.

See also: [Evals as a release gate](/ai-radar/techniques/#evals-as-a-release-gate), [LLM observability tools](/ai-radar/tools/#llm-observability-tools).

<div data-radar data-label="BERT variants" data-ring="adopt" />

## BERT variants

[Bidirectional Encoder Representations from Transformers (BERT)](https://huggingface.co/docs/transformers/en/model_doc/bert) revolutionised NLP by processing words in relation to their entire context rather than sequentially. The family has continued to evolve, with [ModernBERT](https://huggingface.co/blog/modernbert) the latest iteration, improving training times and accuracy through architectural updates.

BERT-style models serve a different purpose from generative models. Where GPT generates text, BERT models are optimised for understanding tasks such as classification and sentiment analysis. They are also the basis for the semantic vector embeddings that RAG systems use to retrieve relevant context for generative models.

We recommend [DeBERTa](https://huggingface.co/microsoft/deberta-v3-base) for new NLP projects, as it handles word relationships more effectively using a disentangled attention mechanism. [DistilBERT](https://huggingface.co/docs/transformers/model_doc/distilbert) is smaller and faster whilst retaining most performance, valuable for production deployments with strict latency requirements. Domain-specific variants exist for biomedical [(BioBERT)](https://github.com/dmis-lab/biobert) and financial text [(FinBERT)](https://huggingface.co/ProsusAI/finbert), though these require expertise to use effectively.

<div data-radar data-label="Few-shot prompting" data-ring="adopt" />

## Few-shot prompting

Providing examples to guide model responses has proven consistently effective across Large Language Models.

This is shifting. As models become more capable, interactive multi-turn approaches are gaining favour: rather than providing examples upfront, practitioners prompt models to ask clarifying questions and iterate toward a solution. The pattern often produces better results, particularly in agentic workflows where the model can refine its approach.

Reasoning models shift the balance further. OpenAI and Anthropic both advise defaulting to zero-shot for them and stating explicit success criteria the model can check its output against, rather than supplying worked examples, which can even degrade reasoning-model performance. Persona framing has weakened too: research finds that "act as an expert" prompts do not reliably improve factual accuracy, though they still help steer tone and format.

Few-shot prompting retains an important role in non-interactive contexts. System prompts and automated pipelines do not afford clarifying dialogue, and well-chosen examples remain the most effective way to establish output format and domain conventions. We typically see diminishing returns beyond 3-5 examples, with token consumption as the main trade-off.

<div data-radar data-label="Agentic tool use" data-ring="adopt" />

## Agentic tool use

We've moved agentic tool use to the Adopt ring for local, sandboxed environments. AI coding assistants that can edit files, run tests, execute shell commands and perform web searches deliver considerably more value than those limited to conversation.

The ecosystem has matured to support this. Standards such as [MCP](/ai-radar/languages-frameworks/#mcp) and [OpenAI's Function Calling](https://platform.openai.com/docs/guides/function-calling?api-mode=chat) provide reliable integration patterns, while improved [observability tooling](/ai-radar/tools/#llm-observability-tools) lets teams monitor what agents are doing. The [Development Containers specification](https://containers.dev/) makes it straightforward to isolate agent execution.

The risks magnify for applications accepting external user input. Prompt injection attacks remain an unsolved problem. An agent that safely edits files for a developer becomes a liability when processing untrusted input. Our recommendation: adopt for local developer tooling and internal workflows, but proceed with caution for customer-facing systems, treating each tool permission as a potential attack vector.

See also: Visual computer use agents, Model Context Protocol, Temporal.

<div data-radar data-label="Spec-driven development" data-ring="adopt" />

## Spec-driven development

Software engineers working agentically are finding that natural-language prompts are not enough to constrain the behaviour of an AI system. Prompts carry ambiguities that the model resolves silently, and the implementation that emerges may differ from the one the engineer thought they had asked for. Spec-driven development has gained popularity as the response: an agentic engineering practice where a written specification, rather than a conversation, becomes the contract the AI works against.

The practice has moved into the mainstream of agentic engineering over the past year. [GitHub Spec Kit](https://github.com/github/spec-kit) and Amazon's [Kiro](https://kiro.dev/) are the most visible tools: Spec Kit is agent-agnostic, while Kiro ships a dedicated specs mode that generates [EARS notation](https://alistairmavin.com/ears/) by default. Both treat structured markdown as the source of truth, with code generated or verified against it. A parallel revival of [Gherkin](https://cucumber.io/docs/gherkin/) and behaviour-driven development sits in the same middle ground between prose and formal language.

The same discipline shows up as an execution loop inside agentic IDEs: plan, implement, then verify, with the agent producing a plan for review before it writes code and evidence of its own checks afterwards. Google's [Antigravity](https://antigravity.google/) makes this loop the default. Spec-driven development pushes the idea one step earlier, anchoring the loop to a specification rather than a plan the agent drafts per task.

The direction we find most exciting goes further. A specification written in natural-language markdown, even one structured in EARS or Gherkin form, only moves the ambiguity problem one step back. The prose may be richer than a prompt, but it still relies on the model to disambiguate it. We are following formal specification languages instead, including our own [Allium](https://github.com/juxt/allium), an open-source language that captures system behaviour in a structured, machine-readable form. Allium is early in its life and external uptake remains nascent, but in our own work it gives AI agents an unambiguous reference and lets engineers detect contradictions before any code is written.

See also: [Formal specification languages](/ai-radar/languages-frameworks/#formal-specification-languages), [Claude Skills](/ai-radar/techniques/#claude-skills).

<div data-radar data-label="Claude Skills" data-ring="adopt" data-change="up" />

## Claude Skills

Claude Skills are reusable prompt templates that codify workflows and domain expertise into repeatable patterns for AI coding assistants. Our teams have found them valuable for drafting proposals, structured debugging, generating commit messages and writing PR descriptions. The common thread is tasks that benefit from consistent approach and structured output. The pattern is no longer specific to Claude: reusable, file-based skill definitions are becoming a common way to package expertise across coding assistants, and in our own work they are now a default.

Skills provide a simpler solution than [MCP servers](/ai-radar/languages-frameworks/#mcp) for many problems. Where MCP requires implementing a server and managing the protocol lifecycle, Skills are markdown files that encode expertise directly. Skills work well with data that exists as files in your project, since the AI assistant can already read those. MCP extends reach to running services and systems beyond filesystem access.

# Trial

Promising approaches with growing adoption, worth exploring for teams ready to invest in emerging patterns.

<div data-radar data-label="Cross-encoder reranking" data-ring="trial" />

## Cross-encoder reranking

[Cross-encoder reranking](https://sbert.net/examples/applications/retrieve_rerank/README.html) enhances AI search and chat systems by examining initial search results more carefully. While embedding search is fast and good at finding broadly relevant content, cross-encoder reranking excels at understanding subtle relevance signals by examining the query and potential results together.

Most teams use a two-step process: embedding search finds 50-100 potentially relevant items, then cross-encoder reranking sorts these candidates to surface the most relevant. The technique often reduces confabulations in downstream LLM responses by ensuring higher quality context selection. Implementation has become straightforward with libraries such as [sentence-transformers](https://www.sbert.net/) providing ready-to-use models. Teams should be mindful of the additional latency and may need to tune the number of candidates based on performance requirements.

<div data-radar data-label="Ontologies for AI grounding" data-ring="trial" />

## Ontologies for AI grounding

As AI systems scale beyond isolated experiments, shared meaning becomes critical infrastructure. Ontologies provide what LLMs lack: authoritative definitions of entities and relationships that don't shift with statistical probability. They ground responses in agreed definitions, enable knowledge graph traversal that pure RAG cannot achieve and support the structured outputs that agentic systems require.

Traditional ontology development tends toward two failure modes: academic approaches aiming for formal completeness using OWL, and pragmatic approaches creating spreadsheets that grow unmaintainable. The key is to start lightweight and formalise selectively. Mark Burgess [argues](https://arxiv.org/abs/2512.19084) that traditional ontologies impose rigid hierarchies that don't match how language models represent meaning, proposing alternative graph structures designed to work with vector embeddings. For organisations needing to ground AI in domain knowledge today, ontologies offer a practical path with mature tooling.

Graph databases such as [Neo4j](https://neo4j.com/) provide accessible implementation options, while [LinkML](https://linkml.io/) offers YAML-based modelling without deep ontology expertise. Start with a painful, high-value domain rather than attempting to model the entire organisation.

See also: LinkML, Neurosymbolic AI, Prolog.

<div data-radar data-label="Model distillation & synthetic data" data-ring="trial" />

## Model distillation & synthetic data

[Model distillation](https://platform.openai.com/docs/guides/distillation/model-distillation) involves training a smaller, more efficient model to mimic a larger one. A common pattern uses LLMs to generate synthetic training data for the smaller model: the large LLM acts as a "teacher", creating diverse examples that help the "student" learn desired behaviour. This makes AI deployment more practical for edge devices or resource-constrained environments.

We're keeping it in Trial because the process requires considerable expertise. Teams need to validate the quality of generated training data and ensure the distilled model maintains acceptable performance. There is ongoing debate about amplification of biases through this approach.

Check the licence of models used for distillation. Llama forbids using its output to train other models.

<div data-radar data-label="Structured RAG" data-ring="trial" />

## Structured RAG

Structured RAG extends basic RAG by organising retrieved knowledge as graphs, schemas or typed records rather than flat text chunks. Microsoft's [GraphRAG](https://microsoft.github.io/graphrag/) uses an LLM to build a knowledge graph from source documents during indexing, then queries that graph at retrieval time. This addresses a weakness in standard RAG: questions requiring synthesis across many documents rather than finding a single relevant passage.

GraphRAG has matured since our last radar. [LazyGraphRAG](https://microsoft.github.io/graphrag/posts/lazyGraphRAG/) reduced indexing costs to a fraction of the original, removing the biggest barrier to adoption. [Neo4j](https://neo4j.com/) provides [dedicated examples](https://github.com/neo4j-product-examples/graphrag-finserv) combining graph-based retrieval with LLM generation.

The trade-off remains upfront investment. Graph-based indexing requires more compute and design than vector-based RAG, and the knowledge graph must be maintained as source documents change. If your queries are primarily about finding relevant passages, standard RAG with [cross-encoder reranking](/ai-radar/techniques/#cross-encoder-reranking) may suffice. If they require reasoning across documents, structured approaches justify their cost.

See also: [RAG](/ai-radar/techniques/#rag), [Ontologies for AI grounding](/ai-radar/techniques/#ontologies-for-ai-grounding), [Cross-encoder reranking](/ai-radar/techniques/#cross-encoder-reranking).

<div data-radar data-label="Orchestrator-worker agents" data-ring="trial" data-change="new" />

## Orchestrator-worker agents

Breaking a task across several agents works best with a clear division of labour: a single orchestrator holds the wider context and delegates self-contained subtasks to worker agents, each with its own context window, which report their findings back to the orchestrator. [Anthropic's multi-agent research](https://claude.com/blog/building-multi-agent-systems-when-and-how-to-use-them) describes this hierarchy, and the pattern is now built into tools such as Claude Code's agent teams.

It is tempting to go further and build teams whose workers collaborate directly with one another. The benefits rarely justify it: without an orchestrator holding the thread, agents take conflicting actions that must later be unpicked, which is the core of [Cognition's case against multi-agent systems](https://cognition.com/blog/dont-build-multi-agents). The working rule is a single writer: keep decisions and edits on one thread, and let extra agents contribute read-only intelligence rather than actions.

The approach is also expensive: running several agents in parallel, each with its own context, consumes far more tokens than a single one. Anthropic notes it is a poor fit for tightly interdependent work such as writing code, where one change depends on the next. Some practitioners find that a well-structured [AGENTS.md](https://agents.md/) and the orchestration primitives already in their coding tool cover most needs, with dedicated frameworks worth adding only for cross-tool or long-running workflows. We reserve orchestration for tasks that decompose cleanly, such as parallel research or breadth-first search across a large codebase, which is why it sits in Trial rather than Adopt.

See also: [Agentic tool use](/ai-radar/techniques/#agentic-tool-use), [Spec-driven development](/ai-radar/techniques/#spec-driven-development), [Agent memory architectures](/ai-radar/platforms/#agent-memory-architectures).

<div data-radar data-label="Evals as a release gate" data-ring="trial" data-change="new" />

## Evals as a release gate

An AI system has no compiler to flag a regression. A reworded prompt, a model upgrade or a new tool can make the output quietly worse, and often the first anyone hears of it is a user complaint. Teams have converged on the same defence: treat evaluations as regression tests and run them in the pipeline, scoring a fixed set of cases on every change and blocking the release when a score drops below a threshold or falls behind the last known-good baseline. As Simon Willison [puts it](https://simonwillison.net/2026/Jul/31/smevals/), evals are regression tests for non-deterministic systems, there to catch the day the model gets worse at the one thing you were relying on.

What you gate on depends on the system. A sensible core is task accuracy against a labelled set, cost per request, latency, and resistance to jailbreaks, each read against a baseline rather than as a bare number. Agents need more: whether the model chose the right tool and stuck to its plan. Structured outputs need their schema checked, and retrieval needs its answers traced back to the source. The judgements too nuanced for a simple assertion are where [LLM-as-a-judge](/ai-radar/techniques/#llm-as-a-judge) does the work.

The tooling makes this routine. [Promptfoo](https://www.promptfoo.dev/) and [DeepEval](https://deepeval.com/) run assertions that fail a build outright; [Langfuse](https://langfuse.com/) and [LangSmith](https://www.langchain.com/langsmith) ship regression gates as ready-made CI actions. Even the [observability tools](/ai-radar/tools/#llm-observability-tools) have added gates of their own, so the same eval that helps you debug a run can also stop a bad one reaching users.

We put it in Trial. The gate is well supported and pays for itself wherever a quiet regression would be costly to find in production, and for regulated teams it gives Model Risk Management an auditable quality bar. The stronger claim, that you should write the evals first in the style of test-driven development, is contested: [Hamel Husain](https://hamel.dev/blog/posts/evals-faq/should-i-practice-eval-driven-development.html) argues for writing evaluators against the failures you have already seen, rather than ones you imagine up front. Begin with the few cases you know are critical, and let the suite grow from the incidents you hit in production.

See also: [LLM-as-a-judge](/ai-radar/techniques/#llm-as-a-judge), [LLM testing frameworks](/ai-radar/languages-frameworks/#llm-testing-frameworks), [LLM observability tools](/ai-radar/tools/#llm-observability-tools), [AI red teaming tools](/ai-radar/tools/#ai-red-teaming-tools), [Production AI monitoring platforms](/ai-radar/platforms/#production-ai-monitoring-platforms).

<div data-radar data-label="Harness engineering" data-ring="trial" data-change="new" />

## Harness engineering

An agent is a model plus a harness: the code around the model that assembles its context, chooses and prunes its tools, runs its loop, holds its memory and checks its work. As frontier models converge, the harness is where a system's reliability is won or lost. A capable model wrapped in a poor harness flails, while a modest one inside a good harness gets useful work done. The discipline was named only this year, by [Mitchell Hashimoto](https://mitchellh.com/writing/my-ai-adoption-journey) and then by both major labs ([Anthropic](https://www.anthropic.com/engineering/harness-design-long-running-apps), [OpenAI](https://openai.com/index/harness-engineering/)), and it has quickly become the centre of gravity for teams building agents.

Much of the craft is subtraction and structure. Vercel [removed 80% of an agent's tools](https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools) and accuracy rose: a smaller, more focused toolset leaves less room for the model to go wrong. Tool design is only half of it. Choosing the right loop for the task, and giving it a stop condition the model cannot simply declare met, is what separates an agent that finishes from one that calls the job done too early. For long-running work, context is reset rather than left to grow, with a compact handoff rebuilding a fresh session so quality does not decay as the window fills.

We put harness engineering in Trial. The vocabulary is only months old and the patterns are still settling, with no agreed tooling or measurement, but the practices pay off today and we already apply them in our own work. Teams standing up agents should treat the harness, not the model, as the thing they are building.

See also: [Agentic tool use](/ai-radar/techniques/#agentic-tool-use), [Orchestrator-worker agents](/ai-radar/techniques/#orchestrator-worker-agents), [Spec-driven development](/ai-radar/techniques/#spec-driven-development), [AGENTS.md and steering files](/ai-radar/languages-frameworks/#agentsmd-and-steering-files), [Agent memory architectures](/ai-radar/platforms/#agent-memory-architectures).

# Assess

Emerging or specialised approaches that warrant investigation for specific use cases, but require careful evaluation before adoption.

<div data-radar data-label="Neurosymbolic AI" data-ring="assess" />

## Neurosymbolic AI

Neurosymbolic AI combines neural networks with symbolic reasoning to address fundamental limitations of pure LLM approaches. Neural networks excel at pattern recognition and handling ambiguity, while symbolic AI provides logical reasoning and explainable inference. LLMs understand natural language well but cannot guarantee rule compliance or explain their reasoning in auditable ways.

Fundamentally, this is an architectural problem. LLMs operate through probabilistic pattern matching over language, not causal modelling. As Mark Burgess argues in his [work on semantic spacetime](https://arxiv.org/abs/2512.19084), language models "paraphrase intentional knowledge" rather than tracing actual causal chains. Precise answers to precise questions require systems that explicitly encode what causes what.

This matters most in regulated sectors. Regulatory rules are non-negotiable constraints, not suggestions a model can approximate. Risk models need to know what entities are and how they relate, and compliance requires explainable decision trails. Similar pressures apply across financial services, healthcare and insurance.

Practical implementations range from lightweight to sophisticated. On the simpler end, teams constrain LLM outputs to valid ontology terms or use knowledge graphs to ground RAG retrieval. More advanced implementations use symbolic reasoning engines to validate LLM-generated conclusions. Renewed interest in [Prolog](/ai-radar/languages-frameworks/#prolog) reflects exploration of logic programming alongside LLMs.

We've placed this in Assess because production patterns are still emerging, but organisations in regulated sectors should be experimenting now.

See also: Prolog, Ontologies for AI grounding, Agentic tool use, World models.

<div data-radar data-label="World models" data-ring="assess" />

## World models

World models sit in the Assess ring as an emerging alternative to pure language model architectures for tasks requiring causal reasoning and planning. Where LLMs predict the next token based on statistical patterns in text, world models build internal representations of how environments behave, enabling systems to simulate outcomes before acting.

The field is developing along several paths. [Yann LeCun's Joint Embedding Predictive Architecture (JEPA)](https://ai.meta.com/blog/v-jepa-yann-lecun-ai-model-video-joint-embedding-predictive-architecture/) learns by predicting missing information in an abstract embedding space rather than reconstructing raw pixels or tokens. Meta's V-JEPA and [VL-JEPA](https://arxiv.org/abs/2512.10942) extend this to video and vision-language tasks with significantly fewer parameters than autoregressive alternatives. [Karl Friston's active inference framework](https://www.verses.ai/), implemented by Verses AI in their AXIOM system, takes a different approach rooted in how biological systems model their environments. Rather than chasing reward signals, active inference agents build generative models and act to minimise prediction error, with Verses reporting 60% performance improvement using only 3% of comparable deep learning compute. Generative world models form a third strand, with [NVIDIA Cosmos](https://www.nvidia.com/en-us/ai/cosmos/) and Google DeepMind's Genie 3 creating physically plausible simulated environments for training robots and autonomous systems.

For financial services, [MarS](https://github.com/microsoft/MarS/) from Microsoft Research demonstrates the pattern applied to market simulation, generating realistic interactive market scenarios for forecasting and anomaly detection without real capital at risk. The paper was accepted at ICLR 2025.

The enterprise value: these approaches offer causal modelling rather than statistical pattern matching. An LLM asked "what happens if I do X?" can only paraphrase similar scenarios from its training data. A world model can simulate the consequences. For teams wanting to experiment, Meta's [V-JEPA 2](https://huggingface.co/facebook/vjepa2-vitl-fpc64-256) and [NVIDIA Cosmos](https://huggingface.co/nvidia/Cosmos-1.0-Diffusion-7B-Text2World) models are available on HuggingFace under permissive licences.

See also: Neurosymbolic AI, Physical AI and robotics foundation models.

<div data-radar data-label="LLM reproducibility" data-ring="assess" />

## LLM reproducibility

Large language models are non-deterministic even at temperature zero. This presents a fundamental challenge for regulated industries where Model Risk Management frameworks require reproducible, auditable decision-making. Banking regulations such as OCC/SR 11-7 assume a level of model stability that generative AI does not provide.

The underlying cause extends beyond floating-point arithmetic. [Research](https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/) demonstrates that batch-dependent kernel operations cause outputs to vary with server load rather than input alone. Smaller open weight models on controlled infrastructure tend to achieve more reproducible outputs than larger models served via shared APIs. Where stochastic behaviour is acceptable, the variation must be well-characterised so it can be explained to regulators as a designed property rather than an infrastructure artefact. Prompts and model versions should be treated as versioned code with change control and rollback procedures.

For teams requiring determinism from larger models, [SGLang](https://lmsys.org/blog/2025-09-22-sglang-deterministic/) now offers deterministic inference building on batch-invariant operators, with the [underlying research](https://arxiv.org/abs/2506.09501) selected for oral presentation at NeurIPS 2025. Teams subject to MRM requirements should be actively evaluating their options now.

See also: Neurosymbolic AI, LLM-as-a-judge.

<div data-radar data-label="Hypothetical document embeddings (HyDE)" data-ring="assess" data-published="false" />

## Hypothetical document embeddings (HyDE)

[HyDE (Hypothetical Document Embeddings)](https://arxiv.org/abs/2212.10496) addresses a common problem in search systems: poor performance when searching content that differs from training data. HyDE asks a large language model to imagine what an ideal document answering the query might look like, bridging the gap between how users ask questions and how information is written.

The system creates several hypothetical documents, converts them into embeddings and blends them together. This averaged representation finds real documents that are mathematically similar, often leading to more relevant results than traditional methods. The approach is particularly effective within RAG systems where accurate retrieval is crucial. Teams should evaluate HyDE for cases where high-precision retrieval is needed and the additional latency is acceptable.

See also: RAG, BERT variants, Cross-encoder reranking.

<div data-radar data-label="GEPA" data-ring="assess" data-change="new" />

## GEPA

[GEPA (Genetic-Pareto)](https://github.com/gepa-ai/gepa) optimises the prompts in an AI system automatically, by reflecting on what went wrong rather than by trial and error. It runs the system, reads the traces (reasoning, tool calls, errors) and asks an LLM to diagnose the failures in plain language and propose prompt edits, keeping a Pareto frontier of candidates that do well on different parts of the task. The [paper](https://arxiv.org/abs/2507.19457), accepted at ICLR 2026, reports that it beats reinforcement-learning tuning by up to 20% while using far fewer rollouts, and improves on the previous best prompt optimiser, MIPROv2, by more than 10%.

The appeal for regulated teams is that GEPA works on API-only models without touching weights, and it produces prompts a human can read and review rather than an opaque set of fine-tuned parameters. It depends on a measurable objective, so it fits tasks with a clear evaluation signal better than open-ended generation.

We've placed GEPA in Assess. It is already available through [DSPy](/ai-radar/languages-frameworks/#dspy) as `dspy.GEPA`, but it is early, and the quality of the optimised prompt depends heavily on the evaluation metric you give it. Teams already investing in prompt optimisation should be trying it now.

See also: [DSPy](/ai-radar/languages-frameworks/#dspy), [Spec-driven development](/ai-radar/techniques/#spec-driven-development), [LLM-as-a-judge](/ai-radar/techniques/#llm-as-a-judge).

<div data-radar data-label="Recursive language models" data-ring="assess" data-change="new" />

## Recursive language models

[Recursive language models (RLMs)](https://arxiv.org/abs/2512.24601), from a team at MIT CSAIL, address a familiar problem: model quality degrades as a prompt grows, well before the context window is technically full. Rather than feed a large context to the model, an RLM keeps it as a variable in a code environment and gives the model only the query. The model then writes code to inspect, slice and filter that context, calling itself or cheaper sub-models over the slices it needs, and never holds the whole thing in its own window at once. [Alex Zhang's write-up](https://alexzhang13.github.io/blog/2025/rlm/) reports processing context far beyond any single model's window this way.

The idea generalises the code-execution pattern (CodeAct), the difference being the recursive calls and the treatment of context as a programmable object rather than text to be read in one pass. That also sets it apart from [orchestrator-worker agents](/ai-radar/techniques/#orchestrator-worker-agents), which split a task along a plan; here it is the context that is split, and the model decides how.

We place RLMs in Assess. The research is credible and there is an active open-source implementation, but the results are largely author-reported, latency is unpredictable, and we have seen no production use yet. Worth experimenting with where context length is the binding constraint.

See also: [Agentic tool use](/ai-radar/techniques/#agentic-tool-use), [Orchestrator-worker agents](/ai-radar/techniques/#orchestrator-worker-agents), [RAG](/ai-radar/techniques/#rag).

<div data-radar data-label="Purpose-built classifiers" data-ring="assess" data-change="new" />

## Purpose-built classifiers

Not every decision needs a generative model. So much of what we hand to an LLM is really classification in disguise: routing a request, spotting intent, scoring a document, judging whether an action is safe. A model trained for that job answers in milliseconds and costs a fraction of a frontier API call, and it hands back a label you can reason about, usually with a calibrated confidence attached. Put one in front of an agent to field the easy cases, and the bill for the expensive model falls away.

None of this is new. Encoder classifiers have done the same work for years. [GLiNER](https://github.com/urchade/GLiNER) and [GLiClass](https://github.com/Knowledgator/GLiClass) classify against arbitrary labels with no task-specific training, run on your own hardware, and descend from the same [BERT family](/ai-radar/techniques/#bert-variants) that already sits in our Adopt ring. A small encoder fine-tuned on a few thousand of your own examples will usually beat a hosted alternative on cost and latency, and it keeps the data in house.

The noise this quarter has been about [TypeSafe's Jev](https://typesafe.ai/), a proprietary hosted model that returns a calibrated distribution over a fixed set of answers, reached through its own API or OpenRouter's beta decisions endpoint. Independent testing bears out the speed and the price, but the claim that it cannot hallucinate is overstated, and its benchmark headlines flatter the results underneath. We put the category in Assess. The idea is sound and worth a place in the toolbox, yet there is little reason to hand a closed service work that open encoder models already do on infrastructure you control. Start with the mature open options, and see the proprietary newcomers for what they are: a convenience, not a breakthrough.

See also: [BERT variants](/ai-radar/techniques/#bert-variants), [Small language models](/ai-radar/platforms/#small-language-models), [Evals as a release gate](/ai-radar/techniques/#evals-as-a-release-gate).

<div data-radar data-label="Fine-tuning with LoRA" data-ring="assess" />

## Fine-tuning with LoRA

[Low-Rank Adaptation (LoRA)](https://huggingface.co/docs/peft/main/en/conceptual_guides/lora) makes model customisation more practical by adding a small set of trainable parameters while keeping the original model unchanged, reducing computing requirements by 3-4 orders of magnitude while maintaining most of the performance of full fine-tuning.

Tools such as Lightning AI's [lit-gpt](https://github.com/Lightning-AI/litgpt/tree/main) and [axolotl](https://github.com/axolotl-ai-cloud/axolotl) support implementation. We place it in Assess rather than Trial because successfully applying LoRA still requires significant ML expertise and careful attention to training data quality. Fine-tuning ties you to a specific model architecture, and given the pace of AI advancement, tomorrow's general-purpose models may outperform your carefully tuned older models. Migrating fine-tuned weights between architectures is particularly challenging. LoRA should only be deployed when the immediate business value clearly outweighs the technical and opportunity costs.

<div data-radar data-label="Physical AI and robotics foundation models" data-ring="assess" />

## Physical AI and robotics foundation models

Physical AI represents the convergence of foundation model capabilities with robotics. Where traditional robotics relied on brittle, task-specific programming, robotics foundation models enable machines to generalise across tasks and adapt to novel situations.

The technical breakthrough is Vision-Language-Action (VLA) models, which extend vision-language models to include physical action outputs. [NVIDIA's Isaac GR00T N1](https://developer.nvidia.com/isaac/foundation-models) represents the first open humanoid robot foundation model, using a dual-system architecture that separates deliberate planning from rapid reactive control. [Google's Gemini Robotics](https://deepmind.google/discover/blog/gemini-robotics-brings-ai-into-the-physical-world/) is advancing similar capabilities. World Foundation Models complement these by enabling simulation-based training: [NVIDIA Cosmos](https://www.nvidia.com/en-us/ai/cosmos/) generates physically plausible synthetic environments that can train robots on scenarios too dangerous or rare to capture in the real world.

Production deployments remain concentrated in well-resourced organisations. The gap between research demonstrations and reliable industrial deployment is substantial. Hardware costs have fallen substantially over the past few years, but perception and control challenges in unstructured environments remain formidable. Organisations with physical AI ambitions should be experimenting, while approaching production timelines with caution.

See also: Digital twin platforms, World models.

<div data-radar data-label="CaMeL" data-ring="assess" />

## CaMeL

[CaMeL (CApabilities for MachinE Learning)](https://arxiv.org/abs/2503.18813) is a defence architecture from Google DeepMind for mitigating prompt injection in agentic systems. The paper, _Defeating Prompt Injections by Design_, treats prompt injection as a problem to be solved structurally rather than through prompt cleverness or red-teaming alone. The architecture splits responsibilities across two models: a privileged P-model processes only user instructions and emits a program defining execution steps, while a quarantined Q-model handles external data but cannot call tools directly. A custom interpreter tracks data provenance, enforcing capability-based security so untrusted data cannot escalate privileges. The implementation is [open source](https://github.com/google-research/camel-prompt-injection).

Prompt injection is the dominant unsolved problem for agentic systems, and it appears throughout this radar: in [MCP](/ai-radar/languages-frameworks/#mcp), in [agentic tool use](/ai-radar/techniques/#agentic-tool-use), in [AI red teaming tools](/ai-radar/tools/#ai-red-teaming-tools) and in our Hold placement for [OpenClaw](/ai-radar/tools/#openclaw). Most current defences are statistical: filters, classifiers, evaluation harnesses. CaMeL is one of the first credible attempts to make the architecture itself prove that untrusted data cannot reach privileged operations. On the AgentDojo benchmark it solves 77% of tasks with provable security guarantees, often reducing successful attacks to zero. Simon Willison has [a useful walkthrough](https://simonwillison.net/2025/Apr/11/camel/) for readers wanting an accessible introduction.

We've placed CaMeL in Assess because it addresses prompt injection more rigorously than anything else we have seen, but production patterns have not yet emerged. The limitations are real: users must define security policies, which carries fatigue risk; running two models adds latency and cost; and the approach has not been battle-tested at scale. For teams building agentic systems for regulated industries, this paper is required reading.

See also: [Agentic tool use](/ai-radar/techniques/#agentic-tool-use), [Visual computer use agents](/ai-radar/tools/#visual-computer-use-agents), [OpenClaw](/ai-radar/tools/#openclaw).

# Hold

Not recommended for new projects; better alternatives exist.

<div data-radar data-label="Word2Vec & GloVe" data-ring="hold" data-published="false" />

## Word2Vec & GloVe

We've placed both [GloVe (Global Vectors for Word Representation)](https://nlp.stanford.edu/projects/glove/) and [Word2Vec (Word to Vector)](https://www.tensorflow.org/text/tutorials/word2vec) in the Hold ring of our techniques quadrant. While these word embedding techniques were groundbreaking when introduced and served as fundamental building blocks for many NLP applications, they have been largely superseded by more advanced approaches.

These older embedding techniques, though computationally efficient, lack the contextual understanding that modern transformer-based models provide. Modern large language models and contextual embeddings such as BERT produce more nuanced representations that capture word meaning based on surrounding context, rather than the static embeddings that GloVe and Word2Vec generate. For new projects, we recommend exploring more recent embedding techniques (see "BERT Variants" in our Adopt ring) unless you have very specific constraints around computational resources or model size that make these older approaches necessary.

<div data-radar data-label="Zero-shot prompting" data-ring="hold" data-published="false" />

## Zero-shot prompting

Zero-shot prompting, the practice of asking Large Language Models to perform tasks without examples or training, has been a quick way to get started with AI. However, we strongly recommend against using zero-shot prompts in production without appropriate guardrails and safety measures. We've heard of multiple incidents where unprotected prompts led to harmful or inappropriate outputs, potentially exposing organisations to significant risks.

Our view is that zero-shot prompting should always be combined with input validation and output filtering. While it can be valuable for prototyping and exploration, moving to few-shot prompting or fine-tuning with careful guardrails is a more robust approach for production systems. The current placement in Hold reflects our concern about organisations rushing to deploy unsafe prompt patterns rather than taking the time to implement proper controls.

<div data-radar data-label="Chain of thought (CoT)" data-ring="hold" />

## Chain of thought (CoT)

[Chain of Thought (CoT)](https://learn.microsoft.com/en-us/dotnet/ai/conceptual/chain-of-thought-prompting) has moved to Hold. While useful when it emerged, [research from Wharton's Generative AI Labs](https://gail.wharton.upenn.edu/research-and-insights/tech-report-chain-of-thought/) demonstrates diminishing returns: gains are rarely worth the time cost, and for reasoning models such as o3 and GPT-5.2, CoT prompting can decrease performance since step-by-step reasoning is already internalised at the architecture level.

For non-reasoning models, CoT still shows modest benefits on mathematical and symbolic reasoning tasks, but these are precisely the domains where better alternatives are emerging. Dedicated reasoning models handle them natively, while neurosymbolic architectures offer more reliable solutions by coupling LLMs with explicit reasoning engines.

The frontier of prompt engineering has moved to structuring problems effectively. Frameworks such as the 5 Whys and inversion now offer more value than CoT prompting. Step-by-step reasoning is now handled by the models and architectures rather than the prompts.

See also: Neurosymbolic AI.

<div data-radar data-label="AI pull request review" data-ring="hold" />

## AI pull request review

AI's code review capabilities have improved substantially. Developers who work effectively with multi-turn AI conversations can now get useful feedback at every level: syntax issues, architectural patterns and subtle runtime concerns such as race conditions.

Yet we've kept AI Pull Request Review in Hold, for organisational rather than technical reasons. PR review isn't just about finding errors; it's a knowledge-sharing mechanism where senior developers mentor juniors and the team maintains awareness of how the codebase evolves. Teams who delegate review to AI often see a decline in collective code ownership.

We recommend using AI as a first-pass reviewer to catch issues before human review, but preserving the human step as deliberate practice for team alignment and knowledge transfer.
